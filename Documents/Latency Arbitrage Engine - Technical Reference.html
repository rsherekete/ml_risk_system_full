Latency Arbitrage Detection Engine

How the engine is built: where its data comes from, how each trade is marked out and classified, how accounts are scored and gated, and what it emits for review and automation. Everything here is taken from the code in notebook-webapp/webapp.

Code as of 16 Sep 2026 Mode shadow (decisions logged, not executed) Spec P1_Risk_Detection_Formal_Specification.docx
Section numbers. Comments in the code (for example “s5.3”) cite the numbering of the older Latency Arbitrage Detection Engine.docx, which only covers Engine A. The P1 specification is now the binding document, and its §5 is Engine B. This reference follows the code’s numbering and states it where it matters.

01Overview

The engine looks for clients who profit from stale broker prices. The signature is a fast, paid trade whose favourable markout appears within the first second and fades by 60 seconds. A move that holds or keeps growing is treated as directional (informed) flow and never counted as latency arbitrage.

It runs as a periodic batch scan over the last 7 days of closed trades, inside the web app process. Each scan:

  • marks every trade out against the broker’s own MySQL tick tape at seven horizons (100 ms to 60 s),
  • checks qualifying trades against an independent reference market (a Vantage Raw ECN live account),
  • scores each account on the spec’s seven weighted components, with confidence reported separately,
  • assigns a band and a verdict, capped at monitor when an alert gate fails,
  • attaches stable automation tags, writes changes to an audit log, and caches the result for the Latency tab.

Engine B (Toxic Flow) runs inside the same scan and reuses its markouts, as P1 §12 requires one shared Markout Engine.

Clock decisions (all measured on 15 Sep 2026)

  • Live Kafka quotes are excluded from markouts. Their event_time is the broker’s publish time, about 90 ms after the tick, which would bias an entire sub-second horizon. Markouts read only server LIKE 'mysql:%'.
  • MT4 millisecond times. tradeRecord.timeStamp is the execution clock: the record’s own market bid/ask equals the MT4 tape at that exact stamp for 94% of events. The match falls to about 55% at ±100 ms and about 10% at ±250 ms. An event is joined to a trade on (server, order) and the same second as the warehouse open or close. This handles pending-order activations and ignores SL/TP modifications.
  • Warehouse and ticks.tm are both UTC (_TICK_TZ_OFFSET = 0). The old +3 h shift was off by about $12 on gold.
  • Vantage is on server time: UTC+3 in summer, UTC+2 in winter. The offset is calibrated per UTC day and never hard-coded (see §07).
  • Millisecond fill. A fill counts as millisecond-stamped when its open time has a non-zero sub-second part. Only these fills get the 100–500 ms horizons and quote age. An exact .000 fill loses them, about 1 in 1,000.

04Scan pipeline

scan() never computes on the request thread. It serves the last result from memory or disk, and on refresh starts a single background build under _SCAN_BUILD. The build is _scan_inner(rules). Each stage writes a heartbeat to artifacts/latency_scan_progress.json; the stage names are shown next to each step.

  1. Load tradesload_trades7-day window. An empty window still returns a full-shaped result (KPIs and mode) so the tab renders.
  2. Exclusions (s5.1)excludedCase-insensitive fnmatch patterns on the raw or canonical symbol and on the platform account group (client_profile). Row ids are renumbered afterwards.
  3. MT4 millisecond timesmt4_ms_timesIf the Kafka backfill is more than 6 h old, a detached refresh is started for the next scan; this scan doesn’t wait for it. On failure, MT4 keeps its 1 s + 5 s fallback window.

05Markout engine

For each trade and horizon h, the engine takes the last broker quote at or before open_time + h on the trade’s own feed (DuckDB ASOF LEFT JOIN on feed and canonical symbol). The markout is signed so that positive means in the client’s favour:

markout_h (bps) = direction × (mid(open_time + h) − open_price) / open_price × 10⁴
  • Feed mapping (_feed_of): servers containing dubai map to mt5_dubai_live01, indonesia to mt5_indonesia, other mt5* servers to themselves, and every MT4 server to one shared mt4 tape. If the own feed has no quotes for the symbol, the MT4 tape is used first, then any other feed.
  • Marking against open_price, not the entry mid, so the half-spread cost is inside the markout. That is why the population benchmark sits around −0.4 bps.
  • Freshness: a matched quote older than open_time − 5 s is a coverage gap, and the markout is set to NaN rather than invented.
  • Sub-second horizons (<1 s) are kept only for millisecond fills. A fill truncated to the second can be up to 999 ms early.
  • Quote age = open_time − time of the last quote, recorded for millisecond fills only.
  • Spread ratio = the relative spread at entry divided by the symbol’s median relative spread over the window.
  • Tick coverage = the trade has a 60 s markout.
  • ASOF targets are precomputed plain columns (t_0…t_6). Expressions on the inequality side matched unreliably.

07Independent reference feed

Fetching

  • Credentials are in the git-ignored vantage_reference.yaml (login, password, server, terminal_path). The terminal is a separate portable install at C:\Users\ReginaldSherekete\MT5_VantageReference.
  • Never use the copier’s terminal. An MT5 terminal holds one login, so logging in the reference account there would take the live copier offline.
  • The fetch runs as a subprocess, python -m webapp.latency_reference fetch <request.json>, because MetaTrader5 IPC calls block the interpreter and would stall the copier. It is read-only: copy_ticks_range(…, COPY_TICKS_INFO), no order functions.
  • Pairs needed are (canonical, UTC hour) for every hour holding a fast, paid trade, plus the next hour when the 60 s horizon crosses into it.
  • Hours within the last 2 are always refetched. At most 2,000 pairs per call, newest first, with a 30 min timeout. Symbols the venue lacks are skipped for 24 h (_no_symbol.json).
  • Symbol resolution prefers tradeable symbols, then the shortest name, then aliases (for example USOIL → USOUSD/XTIUSD/…). Futures months map to the cash instrument, and the basis absorbs the premium.
  • Each hour file covers server time [H+2, H+4) so both possible offsets are included.

Calibration

  • Clock: for each UTC day, each candidate offset (2 h, 3 h) is tested on the day’s busiest symbol. Broker ticks (a 40k sample) are ASOF-joined to reference mids, and the offset with the lowest median absolute deviation wins. Days with no result use the most common offset.
  • Basis: per (symbol, day), the median of broker mid − reference mid is added to reference bid, ask and mid. Dislocation then measures a temporary gap, not a permanent difference in price level (gold was about $0.01).
  • Residual alignment after the offset was best at 0 to +150 ms on gold.

08Account curve profile

Built from all of an account’s tick-covered trades, not just fast or paid ones. Conditioning on short holds selects winners, because quick profits get closed while losers are held, and that inflates the long-horizon markout.

  • Per horizon: mean markout mo_<h>_bps and hit rate hit_<h> (share > 0).
  • Early peak is taken over the millisecond window if at least half of the account’s covered fills are millisecond fills, otherwise over the fallback window. decay_pct = (1 − mo_60s / peak) × 100, clipped to [−500, 100].
  • fast_transient peak ≥ 0.5 bps and mo_60s ≤ 50% of the peak.
  • persistent not fast, and some horizon of 1 s or more has a mean ≥ 0.5 bps.
  • neutral otherwise. no_ticks means the account has no coverage.

09Latency Risk Score (s5.3)

Computed per account over tick-covered trades. The early markout and early hit are each measured against a population benchmark for the same precision class (millisecond or second), because every fill starts about half a spread behind. Each component is scaled to [0, 1]:

spec_score = 100 × Σ weightₖ × componentₖ (clipped to 0–100)

Population calibration

With score_calibration.mode = "population" (user decision, 15 Sep 2026), each magnitude component reaches full marks at the 99th-percentile account of the current book. The population is accounts with at least 20 covered trades, or at least 1 event for the event-count and concentration components. The result is bounded below by score_floor, so noise never earns full marks, and above by the fixed score_scale, so the engine never demands more than the standard. mode = "fixed" uses the scale alone. The values used are reported in spec.score_scale.

10Confidence

Reported separately from the score, on a 0–100 scale:

spec_confidence = 100 × ( 0.35 × sample·significance + 0.25 × data quality + 0.25 × persistence + 0.15 × corroboration )
  • Sample = min(covered trades ÷ 50, 1). Significance = Φ(z), where z compares the account’s event count with a binomial at the book’s base flag rate.
  • Data quality = tick coverage × (0.5 + 0.5 × millisecond share).
  • Persistence = min(days with a flag ÷ 3, 1).
  • Corroboration = the reference-validated share of flagged, reference-covered events.

13Feed root cause (s5.5)

latency_reference.root_cause works at the level the data supports: the broker’s aggregated feed per server and symbol. Constituent feed IDs aren’t available (MT5 ticks carry a single “Zeal Gateway” feeder, and MT4 ticks carry none). Over reference-covered trades, per (feed, symbol):

  • Stale-TOB event = a reference dislocation at the fill. Success = a stale-TOB event that also hit early.
  • Columns: executions, events, successes, impact USD, median feed age, median excess age over 300 ms, median |divergence|, distinct clients, rates, and concentration of events.
  • architecture_risk = ≥ 10 events ∧ ≥ 3 clients ∧ success rate ≥ 50%. These conditions become LA_FEED_ARCHITECTURE_RISK and drive the market_data_condition gate.

Near misses

Up to 15 accounts with at least 1 event that aren’t in the table, ranked by score × min(events ÷ 5, 1). Each lists what holds it back (the event minimum or the band) and its three weakest components by missing points.

15Legacy fused score and ML detector

These fields are still computed and shown for comparison, but they don’t drive the verdict: risk is spec_score.

legacy_risk = 100 × (0.30·stat_conf + 0.25·consistency + 0.20·persistence + 0.25·econ_axis) × (1 + 0.35·ml + 0.20·behavioural + 0.10·stale_share + 0.05·event_share + 0.06·illiquid_share)
  • consistency = flagged ÷ trades. persistence = flagged days ÷ span of days. econ_axis = flagged PnL ÷ the p90 of flagged PnL (at least $100). stat_conf = the binomial Φ(z).
  • behavioural = the strongest score among an account’s toxic_flow, persistent_edge, scalper and news_vol profiles, normalised by the p95.
  • ML detector (train_model): LightGBM (400 trees, 63 leaves, balanced classes) on about 190 features. That is 17 tick-free trade-shape features plus the latest account-day corpus row (ad_*). Labels come from tick-covered accounts (≥ 20 covered trades): positive = ≥ 5 flags and ≥ $25 extracted; negative = ≤ 1 flag; accounts in between are left out. Labels accumulate daily in latency_labels. Evaluation uses 5-fold stratified out-of-fold predictions, with the threshold chosen to maximise min(precision, recall). Saved to artifacts/latency_ml.txt and latency_ml_meta.json.
  • ew: the rule-models 5-day early-warning probability for the latency_arbitrage category.
Model state (trained 15 Sep 2026 23:17). AUC 0.967, but only 12 positives, 1 label day, precision 0.30 and recall 0.25 at threshold 0.05. It isn’t reliable yet, which is why it only feeds the legacy score.

20Known gaps and code notes

Spec coverage

  • L6 can’t be measured, and per-feed attribution isn’t possible: constituent feed IDs aren’t recorded. This needs data from infrastructure.
  • Gate minimums for early hit rate, event success and profit concentration are still 0. Calibrate them from spec_distributions.
  • MT4 millisecond match rate: now 96.8% of MT4 opens (930,941 of 961,757) with 26 backfill files. It is sensitive to Kafka retention (about 7–8 days) and backfill freshness.
  • Reference coverage depends on the Vantage symbol list. Symbols without a match score 0 on the reference component, by design.

Code notes for maintainers

  • _independent_verify (the old MySQL second-source check) is no longer called, because the Vantage reference replaced it. The independent_check rule it used is also unused.
  • tiers (75/55/35) in the rules is unused: the verdict now comes from the spec bands (85/70/50/25). Editing it has no effect.
  • The auto_rescan_minutes comment says a scan takes 3–4 min. The last one took about 16.
  • The automation_success KPI is autos ÷ autos, so it always reads 100% once any auto row exists. It doesn’t measure execution success.
  • Within the scan, confidence is first the binomial statistic and is then overwritten by spec_confidence/100. The first value is kept as stat_confidence.
  • Near misses use a fixed 25 for “points short” rather than reading the band table.
  • The ML detector feeds only legacy_risk. With 12 positives it shouldn’t be promoted to the verdict yet.
